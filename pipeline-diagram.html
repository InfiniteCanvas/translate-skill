How a chapter gets translated

Every line keeps its number from source to ebook.

A chapter enters an eight-stage state machine. Two of those stages can stop it, and when one does, the model gets its own rejected text handed back and asked to fix it. Everything else — the glossary, the note history, the plot recap — accumulates across the whole book so chapter 200 is more consistent than chapter 1.

The numbered-line contract translation.md → TRANSLATION_SCHEMA

Four lines went in. Three came out. A plain line-count check says the shape is close enough; the echoed index says exactly where 002 and 003 went. That is the whole reason the protocol exists — dropped and merged lines become structurally detectable instead of off-by-one guesswork.

The stage rail

Chapters run in order, never in parallel — the glossary is meant to grow as you go, so later chapters translate more consistently than earlier ones. Every step below falls into exactly one of three kinds, and the distinction is the thing worth holding onto: a model call costs money and can be wrong, a gate can only stop you, and pure code does neither.

The attempt loop

Three tries, then stop

max_attempts defaults to 3. Each retry re-reads the glossary as it stands now, so attempt two benefits from anything attempt one taught the book. Between attempts the contextual glossary is rebuilt from scratch.

Terminal state

needs-review

After the last attempt the chapter stops and waits for you — it never guesses past its budget. status --why prints why it is stuck, retry sends it back after you fix the cause, and mark accepts a chapter you wrote by hand.

What each stage actually does

The order matters more than it looks: glossary expansion runs after the faithfulness gate accepts, so terms learned from a bad translation never enter the book.

01

Translate

model call

The whole chapter in one call while its expected output fits the packing budget. Longer chapters split into token-budget-packed parts, each still carrying the style guide, the novel background and the previous part's tail as input context.

A part whose response looks truncated retries once at a higher cap. Each validated part is saved as it lands, so a crash or a Ctrl-C costs at most the part in flight. A single source line too long for even the escalated cap fails immediately, with no model call spent.

02

Validate

gate

Line count must match the source exactly, and a line that was empty stays empty. Structural violations become feedback rather than a crash, so the retry is a normal attempt and not an error path.

03

Balance

pure code

Counts every contextual glossary term in the source against the translation, with enough tolerance to forgive hyphenation, inflection and a small edit distance — then reports drift. Fully advisory: nothing fails here.

Drift signals run one cleanup judgment, keeping named entities and named actions while marking class nouns for retirement. That retirement is deferred until the translation is accepted, because a bad translation is exactly what invents false drift.

04

Faith

gate

A reviewer model judges faithfulness line by line and answers with a verdict and its reasons. It also receives the drift signals Balance kept, as term-consistency hints — and it, not the counter, makes the final call on which signals were real.

Failure reasons become the feedback the next attempt is handed.

05

Glossary expand

model call

Proposes new named entities, named actions, and titles bound to a name. A proposal has to earn its place: it is counted across the whole source corpus and added only at or above min_term_occurrences, default 3. New variants ride the same gate.

This is also where Balance's deferred retirements are applied — both happen on the attempt Faith just accepted, and nowhere else.

06

Notes generate

model call

Proposes translator's notes against line indices, aware of the glossary's deliberate renderings so a transliterated or nuance-dropping choice gets a note explaining what the source term literally carries. Notes are tagged cultural, idiom, wordplay, honorific, unit or other; anything self-assessed as low confidence is dropped unless you keep those.

07

Notes dedup

pure code

A note survives only if its term hasn't been annotated within the last tn_gap_chapters, default 10. The per-chapter cap is applied after that, in code — the prompt asks for severity-ordered notes, so what gets trimmed is the least valuable context, not an arbitrary slice.

Every drop is written to a sidecar you can read, so you can see what didn't make it.

08

Assemble

write

Writes translated/CHAPTER_NNNN.md as clean markdown — no footnote markers, no notes section — alongside a notes sidecar, and promotes the chapter's status to translated. Past this point the file is yours to hand-edit; the epub builds from it as-is.

What goes in, and what stays behind

The per-chapter machine above is stateless in the useful sense — it can be read top to bottom and understood. What makes chapter 200 better than chapter 1 is everything on this side of the diagram.

Style style.md

A preset copied in at init — measured literary English, modern voice, elevated epic register — and hand-editable. Your edits apply on the next translate, with no re-init.

Background novel_info.json

Two to four sentences of novel context from the synopsis. It rides along in the [Background Information] frame of every prompt that cares about the wider story.

Story recap story_state.json

One cheap call per chapter folds the previous recap plus the finished chapter into 120 words or fewer, so the model translating chapter N knows what happened in 1–N−1. Advisory only: a recap failure warns and the chapter proceeds without it.

Contextual glossary glossary.json

Not the whole glossary — only the terms that actually appear in this chapter, capped and ordered by frequency, rebuilt at the start of every attempt so a retry benefits from what the failed attempt taught the book.

Glossary growth glossary.json

Seeded from the shipped catalogues at init, then grown by accepted chapters only. Retired terms never come back — not from re-seeding, not from expansion.

Note history tn_history.json

What has been annotated and when. This is what makes a note that explained a term ten chapters ago not explain it again on the next appearance.

Resume point draft/*.state.json

Rewritten after every stage, so an interrupted chapter picks up at the stage it died in rather than at the top. Re-running the same command is always safe.

Chapter history git

One labeled commit per finished chapter. git log is a readable backup of the project, and a changed term can be propagated to already-translated chapters by replacing text instead of retranslating the book.

Any call can fan out

Every model call the pipeline makes — the translation, the faithfulness verdict, glossary expansion, the notes — goes through that job's provider array in config.json. One block is one call. More than one block fans out, and an arbitrator merges.

single block — the common case
prompt→ translator[0]→ ordinary single-model reply
two or more blocks
prompt→ translator[0] translator[1] → arbitrator
Candidates are merged into one reply under the task's own JSON schema, so gates and validators never have to learn about multi-model output.
Two rules worth knowing

The arbitrator is resolved per job — a translation merge and a notes merge can use different models if you author them that way. And a configuration that fans out at all without an authored arbitrator is refused at load rather than quietly resolving to one of the models it is being asked to judge.
